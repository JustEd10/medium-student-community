# Резервные копии и репетиция восстановления

Сервер сохраняет проверенный снимок существующей базы при запуске, затем не чаще одного раза в сутки перед очередной записью. Планировщик сервера проверяет необходимость снимка каждый час, включая периоды без изменений. Для новой базы первый снимок создаётся сразу после первой успешной записи. Частые опросы AI не создают отдельные копии.

По умолчанию снимки находятся в `DATA_DIR/backups`; сохраняются последние 14 проверенных копий. `BACKUP_RETENTION` задаёт целое число от 2 до 365. Повреждённые снимки автоматически не удаляются: они требуют отдельного расследования и могут занимать дополнительное место. Запуски сервера тоже учитываются при ротации; это число копий, а не гарантированное число дней истории.

`BACKUP_DIR` позволяет указать отдельный каталог, в том числе на отдельно подключённом защищённом диске. Каталог не должен совпадать с `DATA_DIR`, в том числе через символьную ссылку. Без явно настроенного и проверенного внешнего хранилища копии остаются локальными: потеря диска может уничтожить и базу, и копии. Само наличие `BACKUP_DIR` не доказывает отдельный диск или удалённое хранение. Синхронизация и внешнее хранилище этой реализацией не настраиваются.

Файлы создаются с правами `0600`, каталог копий — `0700`. Копии содержат логический дамп SQLite — состояние сообщества и отдельные учебные таблицы, включая профили, связи, ограничения пользователей и хеши учётных данных. Они конфиденциальны. Сессии обоих API и их токены исключены; после восстановления пользователи входят заново. Файл содержит версию формата, время создания, JSON payload и SHA-256. Проверяются контрольная сумма и прикладная схема. SHA-256 обнаруживает повреждение, но не является цифровой подписью и не защищает от подмены человеком, имеющим доступ на запись.

Файл снимка записывается через уникальный временный файл с flush и атомарное переименование. Изменения основной базы выполняются транзакцией SQLite. Если обязательный снимок перед изменением не получился, изменение базы отклоняется. После уже успешной первой записи ошибка снимка не превращает сохранение в ошибку: память соответствует диску, а проблема копирования отражается в статусе и журнале. Ошибка фонового снимка также видна в журнале как `BACKUP_UNAVAILABLE` и в `getBackupStatus()` без путей и содержимого. Повреждённая SQLite или невалидный исходный JSON останавливают запуск; пустые данные и автоматическое восстановление вместо неё не подставляются.

## Команды

Выполнять из корня репозитория. Примеры используют собственные тестовые каталоги; не подставляйте рабочую базу для репетиции.

```sh
DATA_DIR=/path/to/test-data BACKUP_DIR=/path/to/test-backups node scripts/backup.mjs create
node scripts/backup.mjs check /path/to/test-backups/snapshot-….json
node scripts/backup.mjs rehearse /path/to/test-backups/snapshot-….json /path/to/new-rehearsal-directory
```

`create` читает существующую `medium.sqlite` (либо старый `db.json` до переноса), не запускает сервер и не создаёт пустую базу. Команды выводят только результат проверки, время и/или количество пользователей, без содержимого, токенов и путей. Найти нужный файл следует в приватном каталоге копий. При ошибке возвращается ненулевой код.

`rehearse` сначала проверяет снимок и затем эксклюзивно создаёт **новый, ещё не существующий** каталог (родитель должен существовать). Даже уже существующий пустой каталог отклоняется. Создаётся `medium.sqlite`, затем проверяются схема, внешние ключи и совпадение восстановленных данных. При восстановлении старого JSON-снимка дополнительно сохраняется исходный `db.json`. Исходная база не заменяется. При ошибке записи новый каталог может остаться для расследования; повторный запуск требует другого нового каталога.

Проверка на синтетических данных: `node --test tests/store.test.js tests/backups.test.js`. Она проверяет сохранение профилей, банов и всех связей, исключение сессий, отказ на повреждении, ротацию, права доступа и согласованность памяти/диска при ошибках. Это не является выполненной репетицией для рабочей базы. Для реального восстановления необходимы отдельно согласованные остановка сервера, проверка выбранной копии и замена данных; CLI намеренно не заменяет рабочую базу.

## Google Диск: подготовленная интеграция

Для личного диска используется OAuth от имени владельца с единственным разрешением `drive.file`: файлы, созданные приложением. Сервисный аккаунт для личной квоты не используется. Google требует OAuth-клиент и согласие владельца; само подключение Google Диска к Codex не выдаёт серверу приложения долгосрочную авторизацию.

Перед отправкой снимок проверяется и шифруется AES-256-GCM с новым nonce. Ключ не попадает в Google Диск. После загрузки файл скачивается обратно, расшифровывается и сравнивается с исходной копией. Проверяется закрытость папки: допустим только владелец, без общедоступных, групповых или доменных разрешений. При изменении разрешений новые загрузки прекращаются до исправления папки.

### Однократное подключение на компьютере владельца

1. В Google Cloud включить Google Drive API, настроить Google Auth Platform и создать OAuth client типа **Desktop app**. Сохранить скачанный JSON вне Git-репозитория. Не отправлять его содержимое в чат.
2. Авторизоваться в Google через локальный скрипт. Примеры путей — шаблоны, а не существующие файлы:

```sh
node scripts/connect-drive.mjs /private/path/desktop-client.json /private/path/drive-backup-config.json /another-private-path/drive-recovery-key.json
```

3. Скрипт выводит локальный адрес на `127.0.0.1`. Открыть его в браузере, выбрать свой Google-аккаунт и подтвердить доступ. Скрипт использует PKCE и проверку state, создаёт новую закрытую папку «Медиум — резервные копии» и сохраняет конфигурацию с правами `0600`. OAuth-коды, токены и ключ не выводятся. Публичный callback на сайте не добавляется. Скрипт не запускается на Amvera.
4. Сохранить **ключ восстановления отдельно от диска хостинга**. Он потребуется при потере сервера; без него облачная копия не расшифруется. Закрытую конфигурацию на компьютере тоже сохранить защищённо, чтобы восстановить авторизацию и ID папки.
5. В отдельном согласованном шаге перенести `drive-backup-config.json` в закрытый `/data` сервера либо указать `DRIVE_BACKUP_CONFIG`. Не загружать конфигурацию в Code, GitHub, публичный статический каталог или в сам Google Диск. Копию ключа восстановления на компьютере на сервер дополнительно не переносить.

Google Auth Platform в статусе Testing выдаёт для этого разрешения refresh token со сроком 7 дней. Для долговременного расписания нужно настроить подходящий режим публикации OAuth-приложения и выполнить требования Google; токен остаётся отзывным. При отзыве доступа или истечении срока панель показывает ошибку, локальные копии сохраняются.

### Работа сервера

После появления закрытой конфигурации сервер отправляет новые ежедневные снимки асинхронно, отдельно от записи основной базы. Неудачная загрузка не отменяет успешное сохранение данных. Каждая часовая проверка повторяет попытку для последнего локального снимка. Состояние синхронизации хранится в `drive-backup-state.json` с правами `0600`; зарезервированный ID позволяет проверить потерянный ответ загрузки без повторного создания того же файла. После перезапуска сохраняется время последней проверенной загрузки. При повторной обработке того же снимка облачный файл и закрытость папки снова проверяются.

Панель администратора показывает отдельный статус Google Диска. «Подключён» и «загружен и проверен» — разные состояния. Без конфигурации модуль не обращается к Google и не имитирует успешное подключение.

В этой версии удаление старых облачных копий **не выполняется**. Локальная ротация сохраняется. В Google Диске будут накапливаться ежедневные снимки; управление сроком хранения можно добавить отдельно. Размер исходного снимка ограничен 4 MiB для multipart upload. При превышении нужно перейти к resumable upload; ошибка отображается, локальный снимок сохраняется.

### Проверка и репетиция

```sh
DATA_DIR=/private/test-data node scripts/drive-backup.mjs upload /private/test-data/backups/snapshot-….json
DATA_DIR=/private/test-data node scripts/drive-backup.mjs verify REMOTE_FILE_ID /private/new-restore-directory
```

`verify` скачивает зашифрованную копию и восстанавливает базу только в **новый каталог**, после проверки ключа, целостности, схемы и связей. Рабочая база не заменяется. Сессии исключены. Другие приватные конфигурации, например ключ GigaChat, в снимок базы не включены.

Выполнены проверки с подставным Google API: шифрование, неправильный ключ, повреждение, приватность папки, повторная попытка, восстановление, состояние после перезапуска, конфигурация и loopback OAuth. Реальный вход, загрузка в пользовательский Диск и подключение к Amvera пока не выполнены.

Официальные инструкции: [OAuth-разрешения Drive](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [OAuth для Desktop](https://developers.google.com/identity/protocols/oauth2/native-app), [сроки refresh tokens](https://developers.google.com/identity/protocols/oauth2), [загрузка файлов](https://developers.google.com/workspace/drive/api/guides/manage-uploads).
